## 一筆資料的邏輯鏈

輸入 `examples/molecules.csv` 的 ethanol 這一列 → 讀取 UTF-8 文字 → 偵測 CSV → 指出 SMILES 欄 → `Chem.MolFromSmiles("CCO")` → 檢查解析成功 → 計算分子量／HBD → 畫 2D 圖 → 寫出 JSON/SDF → manifest 記錄來源與版本。

向教授展示時，先打開輸入、再打開核心函式、再打開輸出，最後改一筆為 INVALID，展示錯誤如何被記錄。這比只展示一張成功畫面更能說明理解。

## 建議驗收標準

1. 每個宣稱支援的格式都有正確、損壞、邊界案例；支援矩陣與實際 reader 一致。
2. 已知格式標記優先於錯誤副檔名；弱線索需要驗證，不能宣稱萬無一失。
3. 多個候選結構欄要讓人選，或採用明確可檢驗的規則，不默默選第一欄。
4. 失敗的記錄可找回原文及原因；全部來源記錄都能在成功／失敗計數中對上。
5. 對適用格式測試往返：立體化學、同位素、形式電荷、片段、座標、metadata 分別檢查。化學圖相同不等於原始檔逐位元相同。
6. 真實資料另建人工標記驗收集；建議每個主要格式先收集至少 100 個檔案或依實際分佈取樣，報告來源與難度，避免把多筆 SDF 的分子數當成獨立格式檔數。
7. 記錄格式辨識正確率、拒絕／歧義率、有效分子讀取率、誤接受率、往返保真率、p50/p95 耗時與版本；分母及排除規則必須寫明。
8. 新電腦可依 README 跑通；Windows 原機測試需另存證據。本包的 Linux 測試不能冒充 Windows 實測。

目前固定範例測試只是回歸檢查，不代表上述真實資料驗收已完成。

## GitHub 交付也是必須完成的工作

建議新倉庫名稱：**chem-structure-converter**。名稱直接表達化學結構的輸入、偵測與轉換；應用顯示名稱仍為 ChemBridge。新 repo 預設 private；如已有明確公開要求則採用 public。

執行者必須按照 `docs/GITHUB_DELIVERY_zh.md` 建立新 repo、commit、push、核對遠端 SHA，再從新目錄 clone 並重跑 README 的步驟。不能只回傳一段命令或只完成本機 commit。若遠端名稱已被佔用，不可覆寫不相關倉庫，可建立有日期尾綴的新名稱並記錄。

推送前排除密鑰、.env、.venv、私人資料及使用者上傳。只納入原始碼、合成範例、文件、提示詞和適當測試證據。若執行環境沒有 GitHub CLI／登入，先完成可供推送的本機工作，清楚標成等待 GitHub 存取；不得聲稱已 push。

## 第二階段：擴格式

依使用者真的上傳甚麼，先選一種擴充。Open Babel 是可評估的多格式工具，但轉換成功不保證化學資訊完整。先建立各格式的能力表：可讀／可寫、是否有鍵級／立體化學／座標／電荷，以及哪些欄位會遺失。

XYZ 通常僅含元素與座標，不能把推斷鍵當成原始真值；CIF/mmCIF 也要分清晶體／大分子用途。對每種推斷都應在輸出中標示。圖片／PDF 結構辨識則獨立立項，先抽取結構再經 RDKit 驗證，不能把文字 OCR 等同分子圖辨識。

## 第三階段：是否接 torch-molecule

先回答：要預測哪個目標？單位？有甚麼標籤／checkpoint？訓練資料適用哪些分子？評估怎樣做？這些不清楚就先做好格式工程。勿為了用框架而訓練模型去近似本來就能直接計算的分子量。

## 工程與論文的分界

一般格式互轉已有成熟工具；單純包裝 reader、writer 和 UI 不能直接宣稱足以發表 ICML/NeurIPS/ICLR。基於此 MVP 可以提出待驗證的研究問題：

- **歧義與拒絕**：系統如何知道不能可靠自動判定？比較 extension-only、signature+parser、本工具的欄位歧義策略；測試 coverage 與誤接受率的取捨。
- **資訊保留**：定義結構／立體化學／座標／metadata 各層的轉換損失，建立困難且有人工真值的測試集。
- **不完整結構恢復**：在缺鍵級或圖片輸入時，如何校準信心與要求人工確認？這會涉及新的模型或方法。

這些都是候選問題，尚未做新穎性審查、最新文獻綜述或實驗驗證；不能先當作已成立的創新點。
